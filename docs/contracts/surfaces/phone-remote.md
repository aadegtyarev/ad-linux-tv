# Surface contract: phone remote

## Boundary and consumers
The `/remote` web UI on a phone submits browser commands to the TV's Python HTTP service. The service queues commands for the Firefox bridge. This is trusted-LAN HTTP, not a secure Internet-facing remote.

## Inputs, outputs, and flow
- User submits PIN to `POST /api/login`; success sets an HttpOnly, SameSite=Strict, 12-hour session cookie and returns a CSRF token. Service selection comes from `/api/services`; commands post JSON to `/api/command` with CSRF header.
- Commands: `open` with configured service ID, `home`, `back`, `refresh`, `up`, `down`, `left`, `right`, `ok`. Accepted commands return 202; malformed/unknown commands 400, unauthenticated or invalid-origin requests 403, rate limited login 429, full queue 503, oversized payload 413.
- Authenticated `POST /api/input` uses the same session, Origin and CSRF checks, even for a loopback client. It accepts exactly one printable UTF-8 `text` field (1–512 characters) or one allowlisted key (`enter`, `backspace`, `tab`, `shift-tab`, `address`, `escape`). The TV process sends it through labwc's virtual keyboard protocol to the focused Firefox field; input is never queued, logged, stored, or returned. It returns 200 on success, 400 for invalid input, 403 without authorization or outside the TV session, and 503 if keyboard injection is unavailable. The phone form uses Android/iOS's native keyboard and clears submitted text.
- Authenticated `GET /api/audio` reports available TV-user sinks, selected output, volume and mute. `POST /api/audio` with Origin, session and CSRF selects a listed sink, moves current TV audio streams, sets volume within 0–100%, or toggles mute. Errors leave browser commands available. The same controls are available only locally in TV System.
- `/api/status` reports bridge online, pending count and latest failed/uncertain result. UI polls each second, presents accepted/failure/connection-loss messages and forces relogin after 401/403.
- The phone UI keeps Home, Back and Refresh visible near the top. Its address form opens the configured Browser service, waits for the bridge queue to settle, then focuses the Firefox address bar and sends the HTTP(S) address through authenticated input. Website-field text uses the phone's native keyboard and the same endpoint.

## Security and privacy
- Private/loopback source checks apply to `POST /api/login` and command POSTs. Publicly reachable GET surfaces include `/`, `/remote`, `/api/services`, `/api/status`, `/health`, `/api/qr`, and static UI assets: any network source able to reach the bound listener can request them. These return UI, the configured service catalogue/advertised address, QR data, or operational status; they do not return the PIN or session/CSRF secrets. `GET /api/audio` also requires a paired session except for the exact local TV kiosk. `GET /api/local-pin` is the exception: it is available only to the local TV launcher, with loopback source, exact `127.0.0.1:<port>` Host, a launcher request header and kiosk PIN-file configuration. It is denied over LAN and marked no-store.
- Phone login and command POSTs require a private/loopback client source. Phone POSTs also require HTTP Origin to equal Host, a syntactically valid Host, and (for commands) a valid session and CSRF token. This does not verify that the Host address belongs to the server. For loopback local UI POSTs, Host must parse as localhost or a loopback IP. Firefox bridge poll/ack additionally require loopback source, exact `127.0.0.1:<listener-port>` Host, and the bridge header/value.
- No TLS: use only a trusted private LAN; do not port-forward. PIN, search text, and passwords typed on the phone traverse LAN HTTP. Session cookie deliberately lacks Secure for LAN HTTP. The PIN is never returned to LAN clients; config contains a salted PBKDF2 verifier, while the dedicated TV user keeps a private mode-0600 PIN file for local display. Client status uses fixed outcome/reason codes and excludes URLs, PINs, typed text, and exception text. HTTP access logs are suppressed.
- Local TV launcher command submission is intentionally separate from phone authentication.

## Failure, limits, and verification
The in-memory queue is FIFO and bounded to 128; status reports extension offline after 30 seconds, pending commands, and latest failure for up to 300 seconds. A later success does not clear the last failure; a newer failure replaces it. Remote UI displays pending and failure concurrently. Extension execution is at-most-once after claim and may be uncertain/lost on interruption; see [TV launcher](tv-launcher.md).

Automated tests verify authentication, CSRF/origin/security, queue and response semantics. On Beelink, the LAN remote and QR returned 200, authenticated text reached Firefox in Cyrillic, the managed Browser tab accepted a direct URL with the TV toolbar normally hidden, and Ethernet-to-Wi-Fi failover changed the advertised address and QR in both directions. A real phone session and fresh DHCP lease remain to be checked.

## Non-goals and related contracts
Arrows and OK are guaranteed only on the launcher grid; they are not service-page controls. The HTTP LAN page is not an installable PWA; a stable hostname and trusted HTTPS setup are separate work. No TLS, Internet exposure, exact-once command guarantee, or service/DRM guarantee.
